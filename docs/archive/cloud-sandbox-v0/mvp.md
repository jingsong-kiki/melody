## 本轮目标

在一个管理页面输入仓库地址、分支和问题，点击开始后，服务器创建独立 Docker 沙箱、下载代码，让一个 Agent 自主修改并执行测试，页面最终提供日志、补丁和验证结果。

目标周期为一个工作周；先完成真实执行，再完善页面。最终“只描述问题”的体验见 [产品目标](product.md)，本轮由人工提供仓库来代替自动定位。

## 必须交付

- 单页面提交、任务状态、执行日志、结果下载，以及停止操作。
- 一台 Linux 服务器、单个运行中的任务、一个预选测试仓库所需的运行时和安装/测试配置。
- 每次执行使用独立容器，记录实际拉取的基线 commit。
- Agent 执行后由 Worker 独立运行预设验证命令，记录命令、退出码和输出；区分执行结束与验证通过。
- 导出可应用到基线的补丁，包含新增文件。销毁容器前保存日志和产物。
- 仓库拉取失败、执行错误、验证失败、超时、取消有明确结果；服务重启后未完成运行标记中断，回收其遗留容器。本轮不自动恢复会话。

实现建议沿用先前调研：Python 管理服务、单 Worker、SQLite 和产物目录，执行侧优先实测 OpenHands SDK + DockerWorkspace。SDK 与镜像固定兼容版本；这是待真实运行验证的技术建议。

先使用公开或预配置只读凭证的可信测试仓库，管理入口在受认证的内网使用。任务容器不获得宿主机个人目录或 Docker socket；只有受控 Worker 管理容器。配置资源、运行时长及模型调用预算限制。

## 本轮不做

自动选择仓库、多仓库实际执行、多 Agent、Webhook、远程个人电脑 Host、通用凭证管理、多租户、集群、自动推送和 PR、本地模型推理、任意仓库自动配置依赖。

## 验收证据

1. 页面点击后可查询任务；执行记录包含任务 ID、运行 ID、容器标识、仓库和基线 commit。
2. 一个预设问题在基线上的测试失败，在修改后通过，并保存回归验证结果。只有 Agent 声称完成不算通过。
3. 下载的补丁能应用回干净基线，包含新增文件；日志和测试输出可查。
4. 分别验证拉取失败、超时和手动停止：结果明确，任务容器回收，已有产物仍可访问。
5. 控制服务重启后，原未完成运行有明确中断状态且无无归属容器。

## 推进顺序

第一天先用脚本完成真实 Agent 修复和产物导出；第二天接 API 与任务持久化；第三天接页面；第四天补失败、取消、超时和回收；第五天在目标服务器重复验收并记录操作步骤。若第一天受模型、网络或依赖阻塞，优先解决真实执行，不用 Mock 页面代替验收。

开始部署所需的目标服务器、模型访问配置、验收仓库及问题尚未提供。相关阻塞单独记录，不计为功能验证通过。

# ADR-001：分开仓库定位与执行，先以单体实现

## 状态

Proposed：根据当前对话提出的实现边界；用户确认了最终问题入口和当前 MVP 方向，具体技术结构尚待实现验证。

## 背景

最终目标是只输入问题，由系统定位一个或多个仓库并自主处理。当前需要在一个工作周内打通单仓库沙箱修复。若把用户输入、仓库 URL 和 SDK 会话写进同一个接口流程，自动定位、重试和替换运行时会牵动页面与业务状态；若先建设通用平台，又会延误真实闭环。

## 决策建议

- 同一应用内分开 Task、Run、仓库定位、工作区、Agent 和结果收集职责，用普通模块与函数实现。
- Task 表达问题；Run 表达一次执行及其规格快照；手动选仓库与未来自动定位产出同一种目标清单，V0 仅允许一项。
- 业务状态和产物由应用掌管，SDK 会话和容器标识作为运行资源保存。
- V0 单服务器、单 Worker、SQLite 与本地文件存储。执行技术先按已有调研做真实验证；本决定不要求完整 Fork 任一候选平台。

## 考虑的替代方案

1. 把 clone 和 SDK 执行直接放在提交按钮的同步请求中：起步更快，但长任务生命周期、断线、取消和产物保存难以独立处理。
2. 先建设自动定位、通用插件体系和分布式编排：覆盖面更广，但本轮无法用真实闭环证明额外复杂度的价值。

## 影响与取舍

现在多维护少量执行元数据和职责边界，换取仓库定位与执行实现可分别演进。单体与单 Worker 简化部署，但不提供高可用或并行能力；多仓库协调、自动恢复和公开服务隔离仍需后续设计。容器不挂宿主机敏感目录，控制入口受认证，凭证不进入任务正文与日志。

## 复核时机

首次真实端到端验证后检查边界是否过重或缺失。开始自动定位、多仓库或并发执行前，按具体问题更新设计并记录新决策，避免把远期设想提前变成本轮要求。

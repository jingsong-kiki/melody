# 产品目标：描述问题，系统定位代码并解决

## 摘要

本文帮助产品与开发人员区分最终目标和阶段交付。最终入口只要求用户描述问题，当前 MVP 仍由用户指定仓库。以下是产品规划，不代表当前系统已实现这些能力。

## 已确认方向

用户最终只需描述问题，不必知道仓库地址。系统结合团队的仓库知识，定位一个或多个相关仓库，获取代码，在隔离工作区中自主排查、修改、测试，并返回可检查的结果。

例如：“登录后订单列表加载失败。”系统可以定位相关前端和订单服务；定位不明确时请求补充信息，而不是要求每个用户预先掌握代码归属。

“自主解决”包含尝试失败、缺少信息、需要人工帮助等可解释结果，不承诺任意问题都能自动修复。代码归属判断也不等于修改授权，执行范围必须在团队允许访问的仓库内。

## 演进顺序

### V0：当前 MVP，先证明执行闭环

用户提供问题和单个仓库地址。系统创建独立沙箱、拉代码、执行 Agent、独立验证并返回日志与补丁。详细范围和验收只维护在 [mvp.md](mvp.md)。

### V1：只填问题，系统辅助定位

建立团队仓库目录，先记录仓库职责和获取方式。根据问题选择仓库并解释依据；不确定时澄清或请用户确认。先验证定位准确性和错误定位的回退，再扩大自主执行范围。

这不预设一定需要向量数据库、知识图谱或训练模型；先用规模可控的仓库描述验证效果。

### V2：跨仓库协作解决

支持一次问题关联多个仓库，安排各仓库的修改和联合验证，按仓库交付结果。如何编排、是否多 Agent、如何发布跨仓库变更，届时单独设计和验收。

V1/V2 是方向和建议顺序，未承诺交付时间，也不是 V0 的隐藏要求。

## 衡量效果

当前看一个真实问题是否完成可复现的修复闭环。后续再看仓库定位是否正确、需要用户补充几次、真实修复成功率和人工接手成本；第一版不为这些指标建设独立分析平台。

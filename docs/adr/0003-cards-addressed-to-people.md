# ADR-003：事项卡发给人，接收人一键交给自己的 Agent

## 状态

Accepted：由用户在规划评审中确认。本决策取代 [ADR-001](0001-thread-collaboration-and-native-handoff.md) 中“人与 Personal Agent 分别拥有可被 `@` 的稳定身份”的设定；ADR-001 的手动唤起原则保留，触发方式按本文执行。

## 背景

ADR-001 与 ADR-002 中，每个人都有一个可被单独寻址的 Personal Agent（如 `B-Agent`），其背后隐含一个常驻的个人总代理：替本人接收请求、携带记忆、决定交给哪个工具，必要时自动回答。评审逐项核对这些职责后发现：寻址可以直接用人；理解、回答和拟方案由接收人原有 coding 客户端承担，平台不预设额外 LLM；上下文由事项卡携带；选择客户端和仓库只是接入配置；自动回答与“所有者手动唤起”冲突，不在当前范围。由于每次都由接收人本人唤起，“发给 B”与“发给 B-Agent”在行为上没有区别。

接收人决定交给自己的 Agent 时，不能要求他把网页上的内容复制到工具里，否则事项卡带上下文的价值就丢失了。Claude Code、Codex 与 Cursor 都提供 deep link，可以在本机打开对应工具、填好提示但不自动发送；Claude Code 与 Codex 还能指定工作目录。

## 决策内容

1. **事项卡发给人。** 平台不设独立的 Agent 身份或常驻个人总代理，只保存人的身份和接入配置（默认客户端、本地代码根目录）。
2. **接收人决定由谁处理。** 接收人可以自己回答，也可以交给自己 coding 客户端里的 Agent。
3. **一键交给自己的 Agent。** inbox 详情页提供“交给我的 Agent 处理”，按接入配置生成 deep link，在对应仓库打开新会话并填好只含卡片编号的提示；接收人按回车即为唤起。接收人在工具中看到钩子提醒后，也可以直接让 Agent 处理。Agent 通过 melody 插件按编号读取卡片，经本人同意后写回回复。
4. **交付阶段 1 不需要常驻客户端。** 提醒依靠插件钩子与 inbox 页面的浏览器通知。常驻进程只在“从企业微信或手机远程让接收人电脑上的 Agent 开始工作”时才需要，届时再引入。

## 考虑的替代方案

1. **保留 `B-Agent` 作为可寻址身份，只去掉常驻与记忆含义：** 寻址多一层概念，但在手动唤起下没有行为差异。
2. **网页显示“复制提示”让接收人粘贴到工具：** 不需要 deep link，但多一步手工操作，且容易把卡片全文复制进会话。
3. **常驻客户端收到点击后直接在后台启动 Agent：** 体验最接近“一点就开始”，但要求每个人安装并保持常驻进程，且绕过了接收人在工具中按回车这一自然的唤起确认。

## 影响与取舍

- **正面影响：** 概念更少，接入只需安装插件；接收人从网页到工具不复制任何内容；deep link 只填写不发送，自然满足手动唤起。
- **取舍与限制：** deep link 依赖各客户端注册的链接协议，Claude Code 命令行需要先在本机交互使用过一次；Cursor 不能指定工作目录。以后若要做“本人不在时自动只读回答”，需要重新引入带权限策略的代理身份。

# ADR-002：用事项卡 inbox 取代自建 `#thread` 对话板，企业微信联动后置

## 状态

Accepted：由用户在规划评审中确认。本决策取代 [ADR-001](0001-thread-collaboration-and-native-handoff.md) 第 1 条“一件事一个 `#thread`，人机同场可 `@`”；ADR-001 的手动唤起、原生会话交接、`attempt_id` 防重与 worktree 来源透明继续有效。

## 背景

ADR-001 把协作载体设计为 melody 自建的 `#thread`：成员栏、消息流、输入框和 `@` 寻址。评审发现这套界面让产品看起来像一个与团队 IM 并列的新聊天或办公软件，团队需要多开一个地方讨论，而 melody 的核心价值其实是把一件事的上下文送到对方 Agent、经所有者确认后交给原工具执行、再把结果带回。

企业微信等 IM 的机器人读不到群聊完整上下文，无法承载“人与 Agent 同场讨论”；但其自建应用与智能机器人支持按钮卡片、回调与更新同一张卡，适合承载通知和低风险操作。企业微信接入需要应用配置、回调或长连接、企业审批，前期投入较大。

## 决策内容

1. **一件事一张事项卡。** 事项卡分问题卡与执行卡，携带发起人确认附带的上下文；追问、补充和状态变化挂在这张卡的往来记录里。melody 不提供频道、成员列表或自由聊天流。
2. **三个界面分工。** 原有 coding 客户端负责发起与执行；melody inbox 页面负责事项卡列表、详情与确认单；团队 IM 负责通知与低风险一键操作。
3. **发起入口在原工具。** 发起人在 Claude Code、Codex 中通过 melody skill 一句话发起，由发起人的 Agent 打包上下文，发送前预览附带与不附带的内容。
4. **执行确认不在 IM 卡片上完成。** 确认单需要完整展示 worktree 来源，只在 inbox 详情页或所有者原工具中确认。
5. **分阶段交付。** 交付阶段 1 只做事项卡创建、inbox 展示，以及本机系统通知与原工具钩子提醒；交付阶段 2 接入企业微信；交付阶段 3 实现唤起、确认与 worktree 执行交接。

## 考虑的替代方案

1. **保留自建 `#thread` 对话板，只弱化视觉：** 仍然需要团队在 IM 之外再开一个讨论场所，没有解决“新办公软件”的感受。
2. **完全寄生在企业微信群聊：** 机器人读不到群聊完整上下文，执行确认也放不下 worktree 来源；且接入成本会阻塞第一阶段交付。
3. **以看板或工单列表为中心：** 会滑向 Jira 式的流程管理，与“不替代 ticket tracker”的边界冲突。

## 影响与取舍

- **正面影响：** 团队不需要新的聊天场所；事项上下文由卡片自带，接收方不必回群聊翻记录；第一阶段不依赖企业微信即可交付。
- **取舍与限制：** 交付阶段 1 的钩子提醒只在接收方下一次使用原工具时生效，不是实时提醒；系统通知依赖接收方本机运行 `melody watch`。多人讨论仍发生在团队 IM，只有发起人确认附带的内容进入事项卡。

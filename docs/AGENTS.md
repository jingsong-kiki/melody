# 文档维护规则

本项目采用仓库内的 [DSH dsh-doc-writing](../.agents/skills/dsh-doc-writing/SKILL.md) 的文档管理方法：按读者目的组织内容，一个事实只有一个权威位置，移动文件时同时修复入站链接，操作声明必须有执行证据。行文和过程残留清理由配套的 [dsh-prose-standard](../.agents/skills/dsh-prose-standard/SKILL.md) 与 [dsh-trim-cot-leakage](../.agents/skills/dsh-trim-cot-leakage/SKILL.md) 负责。

## 范围与文档归属

每份文档只回答一个问题。一个事实只在一处写全，别处用链接指过去。

- `product.md` 回答给人什么体验、产品以后往哪走。不写表结构、接口、验收步骤和落地顺序。
- `mvp.md` 回答这一阶段做哪些、不做哪些、怎样算通过。线框、成功失败信号、端到端验收和分阶段范围在这里。不写部件内部怎么连接，不写每个 PR 改哪些文件。
- `architecture.md` 回答系统由哪些部件组成、状态放在哪、部件之间遵守什么。数据、不变量、状态机、接口和失败时的行为在这里。不写用户操作步骤，不写 PR，不写验收命令，不把交付阶段当成章节。哪一阶段才把某个部件运行起来，用一节指向 `mvp.md`，顺序本身不在这里展开。架构文档是提案，不能写成已经实现。
- `phase-1-plan.md` 以及以后的阶段计划回答先做哪一块、改哪些文件、用什么命令验证。不重写一份数据模型或产品理由。
- `adr/` 回答为什么这样选、放弃了什么。沿用 ADR 格式。不把完整规格再写一遍。
- `README.md` 只做导航。评估目录保留原始调研与证据，不维护第二份当前规格。

以上是规划文档，有意保留目标和待实现内容。未来产品运行说明只描述经验证的当前行为，不能把规划复制成已具备能力。产品未来能力不自动进入 MVP。架构里写出的接口不自动成为本轮验收。

目标变化改 product。本轮范围或验收变化改 mvp。部件、数据或接口变化改 architecture。顺序或验证变化改对应的阶段计划。取舍变化改 ADR。

## 编写与验证

普通页面使用可检索的 `description` 元数据、摘要、目录、正文和最终非权威的 `Dev Note`。索引只保留简短介绍与链接；本规则文件和 ADR 保持各自格式，不强加完整页面骨架。没有适用的 DSH 模板时，不伪造 package 类 `kind`。

未解决的探索只放 Dev Note。范围、限制和验收留在 mvp。段落保持一段一行，内部使用相对链接。

当前文档为中文单语，保留既有路径；本项目不是 DSH 源码仓库，不引入其包专用模板、双语侧车或网站生成流程。以后建立双语文档时，再按 skill 同步配对与验证。

编辑后检查相对链接及页面内锚点、元数据与实际内容、提案与已实现状态、事实是否重复维护。涉及运行操作时执行验证；缺少环境或凭证时明确写未验证。MVP 真实验收必须链接运行记录和产物，Mock 或文档检查不代替端到端验证。

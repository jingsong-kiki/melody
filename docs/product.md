# 产品目标：用事项卡 inbox 连接团队成员与各自的 Agent

## 摘要

melody 让团队成员把一件需要同事处理的事，从自己的 coding 客户端一句话发成一张事项卡。接收方在 inbox 中收到后，可以自己回答，也可以一键把这张卡交给自己 coding 客户端里的 Agent 处理，结果回到同一张卡上，消除人工在不同 AI 会话之间复制粘贴上下文。melody 不是新的聊天或办公软件：人在原有 coding 客户端发起和处理，团队 IM 是外围的入口和通知通道，melody 自己只提供承载事项卡的 inbox 页面。以下是产品规划，不代表当前系统已实现这些能力。

## 核心定位与边界

melody 是连接层，不是协作场所。团队已经在 IM 里聊天、在 Claude Code、Codex、Cursor 等工具里和各自的 Agent 工作；melody 只负责把“一件要交给别人的事”打包、送达、跟踪到结束。产品中没有频道、成员列表或自由聊天流，所有往来都挂在某一张事项卡下，只服务这一件事。

事项卡发给人，不发给独立的 Agent 身份。平台不设常驻的个人总代理，也不预设额外平台 LLM；每个人的 Agent 就是他原有 coding 客户端里的 Agent。平台只保存人的身份和接入配置（默认客户端、本地代码根目录），以及事项卡记录。平台只携带发起人明确附带的上下文，不上传原工具的全部私聊，不承诺无损迁移模型私有上下文。

收到事项卡不等于唤醒模型，也不等于授权执行。只有接收方本人在自己的工具中发出提示后，Agent 才开始处理；每次在隔离 worktree 中的真实执行还需要接收方确认方案，平台确认不代替原客户端自身的工具权限审批。

事项卡不是工单。发起只用一句自然语言，不填表、不设优先级或迭代、不做看板列；事项在发起人确认或关闭后结束，不替代团队既有的 ticket tracker。

## 事项卡

一件事对应一张事项卡。事项卡携带完成这件事所需的上下文，接收方不需要回到群聊翻记录。

| 类型 | 用途 | 结束方式 |
|---|---|---|
| 问题卡 | 向同事提问或请求澄清 | 回答后由发起人点“收到”关闭，被确认的回答记为结论；不进入确认、执行或验收 |
| 执行卡 | 请同事改代码或运行命令 | 交付阶段 1 由接收方在自己的工具中处理并回复；交付阶段 3 起经方案确认、隔离 worktree 执行、发起人验收后结束 |

事项卡本身就是一条信息。请求、状态、参与者和往来都在这张卡上，不再拆出另一套事件流来组织它们。参与者是一个发起人、恰好一个负责处理的接收人，以及零个或多个读者。

继续讨论是在这张卡上追加往来。分享是把某人加为读者，读者打开的仍是这张卡，并在自己的 inbox 里出现于「分享给我的」。钩子提醒和「交给我的 Agent 处理」只给接收人。交付阶段 1 只有发起人和接收人，没有读者，也没有分享。

执行卡一旦派生出隔离 worktree，就把工作分支名记在这张卡上，例如 `melody/work-42-attempt-1`。这个名字是卡片和代码事实的对应关系。问答卡没有工作分支名。

## 接收方的三种处理方式

| 方式 | 操作 | 需要什么 |
|---|---|---|
| 自己回答 | 在 inbox 详情页回复 | 浏览器 |
| 在 inbox 交给自己的 Agent | 点“交给我的 Agent 处理”，自己的工具在对应仓库打开新会话并填好提示，按回车开始 | 原有 coding 客户端与 melody 插件 |
| 在工具里交给自己的 Agent | 看到 Agent 的待处理提醒后，说一句“处理 W-42” | melody 插件 |

后两种方式中，Agent 通过 melody 插件按卡片编号读取请求和附带上下文，处理完后把回复写回卡片；接收方不需要在网页和工具之间复制内容。

## 界面分工

| 界面 | 负责什么 |
|---|---|
| 原有 coding 客户端与 melody 插件 | 发起事项卡并由发起人的 Agent 打包上下文；提醒接收方的 Agent 有待处理事项；读取卡片、处理并回复 |
| melody inbox 页面 | 事项卡列表与详情、浏览器通知、自己回答、一键交给自己的 Agent；交付阶段 3 起承载执行确认单 |
| 团队 IM（企业微信，交付阶段 2） | 外围的入口与通知通道：一句话发起事项卡、推送卡片、在卡片上做“收到”“验收”等低风险操作 |

IM 中的操作只改变 melody 服务端上的事项卡状态，不能直接让接收方电脑上的工具开始工作；接收方下一次打开 inbox 或使用自己的工具时看到变化。执行确认只在 inbox 详情页或接收方原工具中完成，因为确认单需要完整展示 worktree 来源，且移动端误触的代价是改代码。

## 完整用户旅程

### 旅程一：问题卡

前端 A 在自己的 Codex 中一句话问 B“退款状态是否包含部分退款”，生成问题卡 Q-17。B 在浏览器收到通知，打开卡片后点“交给我的 Agent 处理”，Claude Code 在 `order-service` 仓库打开新会话并填好“处理 melody 事项卡 Q-17”；B 按回车，Agent 读取卡片、查代码后给出带依据的回答，B 看过后写回卡片。依据不足时 Agent 改为追问，不假装拥有 B 本地未公开的上下文。A 看到回答后点“收到”，问题卡关闭，这条回答记为结论。

### 旅程二：执行卡

1. **A 在原工具发起。** A 在 Claude Code 中请 B 补退款状态接口。A 的 Agent 把当前会话中的接口字段说明和前端调用点打包进执行卡 W-42，并列出附带与不附带的内容；A 预览后发出。
2. **B 的 Agent 收到提醒。** B 正在 Claude Code 里做别的事，提交下一条提示时，Agent 告诉 B 有一张来自 A 的待处理执行卡 W-42。
3. **B 交给自己的 Agent。** B 说“处理 W-42”。交付阶段 1 中，Agent 在 B 当前会话和工作区里按卡片内容处理，权限审批照常由 B 在 Claude Code 中完成，完成后把结论和分支写回卡片。
4. **交付阶段 3 起的执行交接。** B 唤起 Agent 只读生成方案，在确认单上核对做什么、完成条件、依据快照和隔离 worktree 的完整来源（主仓库路径、基准分支与基线 commit、新建 worktree 路径与工作分支名）后确认；本地适配器派生 worktree 并拉起原生会话，需要权限审批时 B 用接手命令继续同一会话。执行期间 A 在卡片上的补充只进入往来记录，扩充范围需要新方案版本并由 B 重新确认。
5. **结果回到同一张卡。** 卡片更新为“结果待 A 检查”，展示结论、测试证据、分支与最新 commit。A 选择“已检查，可以使用”或“需继续调整”；前者结束事项，后者在同一张卡上继续。

## 演进方向

能力分三个交付阶段推进，当前交付范围与验收见 [mvp.md](mvp.md)。

- **交付阶段 1：事项卡、提醒与一键交给自己的 Agent。** 通过 melody 插件从原工具创建事项卡；inbox 页面展示并发出浏览器通知；插件钩子提醒接收方的 Agent；接收方自己回答，或通过 deep link 与插件一键交给自己的 Agent 处理并回复。不需要常驻客户端。
- **交付阶段 2：企业微信入口与通知。** 通过企业微信自建应用或智能机器人一句话发起事项卡、推送按钮卡片、接收回调并更新同一张卡；不写代码的同事也能发起，手机上也能收到提醒和验收。
- **交付阶段 3：方案确认与 worktree 执行交接。** 接收方唤起 Agent 只读生成方案、在确认单上批准，本地适配器派生 worktree 并拉起原生会话，结果自动回传事项卡。

交付阶段 3 之后的方向：

- **继续讨论与分享：** 在同一张卡上追加往来，并把其他人加为读者。首页仍是个人 inbox。读者只在「分享给我的」里看到这张卡。不做公告牌，也不另建事件流。
- **知识沉淀：** 已关闭的问题卡带有问题、有依据的回答和发起人确认的结论，可以作为团队知识。发起人的 Agent 在发起前先检索可见的历史卡片，能回答就不再打扰同事。为此事项卡从交付阶段 1 起记录可见范围、依据的仓库与 commit、所属仓库和结论。
- **团队视图：** 只做由事项卡自然产生的统计（谁在等谁、等了多久、多少由 Agent 处理），不做派活、排期或工作量管理。
- **远程唤起：** 若要在企业微信或手机上点一下就让接收方电脑上的 Agent 开始工作，需要接收方本机运行常驻进程监听服务端；只在出现明确需求时引入。
- **定向自动只读回答：** 在宿主客户端证实可强制只读的前提下，允许接收方授权 Agent 在本人不在时自动回答问题卡；这需要重新引入带权限策略的代理身份。

## Dev Note

本节非权威。交付阶段 2 与 3 的先后由用户按企业微信联动难度确定；执行交接已有本地脚本实测基础（见 mvp.md），如企业微信接入受阻，可考虑先做交付阶段 3。团队 IM 群聊中的讨论不进入事项卡，知识沉淀只覆盖经过事项卡的内容。

低优先级、不进入当前范围：卡片上可以让能打开这张卡的人看见「接收人的 Agent 正在处理」或「空闲」。状态写在这张卡上，由正在处理该卡的插件会话更新。阶段 1 只有参与者能看见。读者要等分享做了之后才能看见。不因此增加事件流，也不在阶段 1 交付。

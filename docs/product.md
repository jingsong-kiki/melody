# 产品目标：团队与 Personal Agent 共享 `#thread` 协作

## 摘要

melody 让团队成员与各自的 Personal Agent 在同一个 `#thread` 直接交流、澄清依赖和交接工作，消除人工在不同 AI 会话之间复制粘贴上下文。需要改代码或运行命令时，由 Agent 所有者确认，交给其原有 coding 客户端在来源清晰的隔离 `git worktree` 中完成，再把同一次执行的状态和结果带回 `#thread`。以下是产品规划，不代表当前系统已实现这些能力。

## 核心定位与边界

一件事一个 `#thread`（例如 `#订单列表退款状态`），按需动态加入多人及其 Personal Agent，允许跨项目协作。人与 Agent 分别显示身份、分别可被 `@`，成员可以直接 `@` 同事的 Agent，无需先私聊同事中转。MVP 不做大协作空间或项目分类树。

Personal Agent 的稳定身份、所有者、参与权限和团队协作记录由平台保存。身份不绑定特定模型、客户端、workspace 或 session。人有权读取的 `#thread` 消息，其 Agent 默认有权读取，不另设消息 mask；可读不代表每句话都唤醒模型，也不代表授权执行。所有者加入 `#thread` 时，其 Agent 自动进入该 `#thread` 的可寻址范围。

主 Agent 负责理解请求、回答问题和拟定执行方案，由所有者接入的原有 coding 客户端承担。平台不预设额外平台 LLM 或万能 root，也不替代 Codex、Claude Code、Cursor 等原有工作台。平台只携带明确选定的团队协作上下文，不上传原工具的全部私聊，不承诺无损迁移模型私有上下文。

每次真实执行必须由 Agent 所有者点头确认；平台确认不代替原客户端自身的工具权限审批。人工操作和深入介入留在原工作台，平台主要呈现协作进度、worktree 隔离来源、关键问题和结果。每个执行工作在 `#thread` 中只留一张状态卡，作为协作执行记录，不替代团队既有的 ticket tracker。

## 两条协作路径

对话路径是提问、唤起理解、回答或澄清，在 `#thread` 留下有引用来源的共同结论，无需创建工作卡。执行路径从对话中产生明确工作方案，经所有者确认后进入原工具及对应 `git worktree`，再将结果带回 `#thread`。

### 响应触发策略

为防止意外消耗模型配额以及防止 Agent 在未获所有者批准前偷跑命令或改代码，MVP 默认采用**所有者手动唤起**：当 `@B-Agent` 收到请求时，系统保存消息与待处理提醒，由所有者 B 点击唤起本地客户端读取该 `#thread` 上下文，生成有来源的回答或拟定工作方案。

## 完整用户旅程

### 旅程一：只需回答，不启动执行

前端 A 在 `#订单列表退款状态` 发消息：“`@B-Agent`，退款状态是否包含部分退款？”系统通知 B 有待处理请求。B 唤起 B-Agent 读取该 `#thread` 已有的接口讨论，B-Agent 直接在 `#thread` 回答并引用相关消息编号。依据不足时直接在 `#thread` 追问澄清，不假装拥有 B 本地未公开的私有上下文。A 回复“那前端按这两个状态展示”，结论留在 `#thread`，流程结束，不创建工作卡。

### 旅程二：需要原客户端在隔离 worktree 执行

前端 A 建立 `#订单列表退款状态`，加入后端 B（B-Agent 随之可被 `@`）。

1. **A 发起自然请托。** A 发送“`@B-Agent`，请补退款状态接口”，附上接口字段说明。普通提及仅作消息；`@B` 只通知 B；`@B-Agent` 标记待 B-Agent 响应，不自动改代码。“+ 请求协助”仅作为可选快捷入口，不强制 A 填工单表单。
2. **B 唤起 Agent 拟定方案。** `#thread` 显示“等待 B 唤起 B-Agent 响应”。B 点击唤起后，B-Agent 读取 `#thread` 上下文并生成工作方案。
3. **生成唯一工作卡并等待 B 确认。** `#thread` 中出现“工作：退款状态接口（等待 B 确认）”。A 可见等待、需补充或拒绝状态；只有所有者 B 能批准 B-Agent 执行。
4. **B 检查方案与 worktree 来源并批准。** 确认单清晰列出：做什么、完成条件、依据的消息快照、目标客户端，以及**隔离 worktree 的完整来源（主仓库路径、基准分支与基线 commit、新建 worktree 路径与工作分支名）**。B 确认的是不可变的方案快照，后续聊天不会静默篡改本次执行。
5. **拉起原客户端可见会话与隔离 worktree。** 适配器按批准快照准备对应的 `git worktree`，拉起 B 默认客户端的原生可见会话，并根据应用级回执在 `#thread` 更新为“已接收 / 执行中”。
6. **B 在原工具接手与介入。** B 直接在原客户端打开或 attach 该会话，查看该 worktree 下的改动、批准宿主工具权限、补充或纠正。团队 `#thread` 只显示“需要 B 在原工具介入”等简要状态，不把 B 的终端细节刷满聊天流。
7. **需求变更隔离。** 执行期间 A 又发“顺便加个退款导出”，该消息仅作为 `#thread` 新消息保存，不自动混入当前执行。若需扩充目标或改动范围，必须生成新方案版本并由 B 重新确认。
8. **结果回传与对话内验收。** 执行完成后，同一工作卡更新为“结果已回传 · 待人工检查”，展示结论、测试证据、该 worktree 的分支与最新 commit 引用。A 直接在 `#thread` 聊天或点选确认结果（“已检查，可以使用”或“需继续调整”），无需走繁琐关单表单。

## 演进方向

### MVP（当前阶段）：单客户端同源交接与两人协作闭环

一次配置默认客户端与仓库主目录，所有者手动唤起响应，确认后在来源清晰的隔离 `git worktree` 中拉起原生可见会话，本人在原工具接手继续，状态和结果回传同一 `#thread`。详细交付范围与试验矩阵维护在 [mvp.md](mvp.md)。

### 后续演进：按需只读自动响应、既有活跃会话直投、多客户端路由

- **定向 `@Agent` 只读自动响应：** 在宿主客户端证实可强制锁死只读（禁写文件、禁执行副作用命令）的前提下，允许所有者开启自动响应，减少发起人等待。
- **既有活跃会话直投（非 MVP 阻塞项）：** 对支持外部事件推送且桌面/终端 UI 实时同步的宿主（如 Claude Code Channels 正式版或 Codex App Server），支持将获批工作插入已打开的指定会话。
- **多客户端与细粒度路由：** 按用户可编辑的主 Agent 说明，根据项目或仓库自动路由到不同的本地或远程客户端环境。

## Dev Note

本节非权威。将“拉起原生可见会话”作为 MVP 基准路线、将“插入已打开的既有活跃会话”列为后续非阻塞增强，以及默认采用“所有者手动唤起”均已由用户拍板确认。

# 产品目标：用事项卡 inbox 连接团队成员与 Personal Agent

## 摘要

melody 让团队成员把一件需要同事或同事 Agent 处理的事，从自己的 coding 客户端一句话发成一张事项卡，对方在 inbox 中收到、由所有者唤起自己的 Agent 回答或执行，结果回到同一张卡上验收，消除人工在不同 AI 会话之间复制粘贴上下文。melody 不是新的聊天或办公软件：人在原有 coding 客户端发起和执行，团队 IM 负责通知，melody 自己只提供承载事项卡的 inbox 页面。以下是产品规划，不代表当前系统已实现这些能力。

## 核心定位与边界

melody 是连接层，不是协作场所。团队已经在 IM 里聊天、在 Claude Code、Codex、Cursor 等工具里和各自的 Agent 工作；melody 只负责把“一件要交给别人的事”打包、送达、跟踪到结束。产品中没有频道、成员列表或自由聊天流，所有往来都挂在某一张事项卡下，只服务这一件事。

Personal Agent 的稳定身份、所有者和事项卡记录由平台保存。身份不绑定特定模型、客户端、workspace 或 session。主 Agent 由所有者接入的原有 coding 客户端承担；平台不预设额外平台 LLM，也不替代原有工作台。平台只携带发起人明确附带的上下文，不上传原工具的全部私聊，不承诺无损迁移模型私有上下文。

收到事项卡不等于唤醒模型，也不等于授权执行。Agent 的回答或方案由所有者手动唤起；每次真实执行必须由所有者确认，平台确认不代替原客户端自身的工具权限审批。

事项卡不是工单。发起只用一句自然语言，不填表、不设优先级或迭代、不做看板列；事项在发起人验收或关闭后结束，不替代团队既有的 ticket tracker。

## 事项卡

一件事对应一张事项卡。事项卡携带完成这件事所需的上下文，接收方不需要回到群聊翻记录。

| 类型 | 用途 | 结束方式 |
|---|---|---|
| 问题卡 | 向同事的 Agent 提问或请求澄清 | 回答后由发起人点“收到”关闭；不进入确认、执行或验收 |
| 执行卡 | 请求同事的 Agent 改代码或运行命令 | 所有者确认方案、在原工具执行、发起人验收结果后结束 |

每张事项卡包含：发起人、接收的 Agent 及其所有者、一句话请求、发起人附带的上下文、当前状态，以及只属于这张卡的往来记录（回答、追问、补充、状态变化）。

## 三个界面的分工

| 界面 | 负责什么 |
|---|---|
| 原有 coding 客户端 | 发起事项卡并由发起人的 Agent 打包上下文；所有者唤起 Agent、执行、介入与接手 |
| melody inbox 页面 | 事项卡列表与详情、执行确认单、往来记录；melody 唯一的自有界面 |
| 团队 IM（企业微信） | 推送事项卡并提供低风险一键操作；每次状态变化更新同一张卡 |

执行确认只在 inbox 详情页或所有者的原工具中完成，不在 IM 卡片上一键完成，因为确认单需要完整展示 worktree 来源，且移动端误触的代价是改代码。

## 完整用户旅程

### 旅程一：问题卡

前端 A 在自己的 Codex 中输入一句话，向 `B-Agent` 提问“退款状态是否包含部分退款”，生成问题卡 Q-17。B 收到通知，唤起 B-Agent 以只读方式回答并给出依据（例如代码位置）；依据不足时 B-Agent 改为追问，不假装拥有 B 本地未公开的上下文。A 看到回答后点“收到”，问题卡关闭。

### 旅程二：执行卡

1. **A 在原工具发起。** A 在 Claude Code 中请 `B-Agent` 补退款状态接口。A-Agent 把当前会话中的接口字段说明和前端调用点打包进执行卡 W-42，并列出附带与不附带的内容；A 预览后发出。
2. **B 收到通知并唤起。** B 收到通知，点击唤起后 B 本机以只读模式运行 B-Agent，读取卡片上下文和仓库代码，生成方案 v1。
3. **B 在确认单上确认。** 确认单列出做什么、完成条件、依据快照、目标客户端，以及隔离 worktree 的完整来源（主仓库路径、基准分支与基线 commit、新建 worktree 路径与工作分支名）。B 确认的是不可变的方案快照。
4. **在原工具执行与接手。** 本地适配器派生 worktree 并拉起 B 默认客户端的原生会话；需要权限审批时，卡片只提醒 B 回原工具，B 用接手命令继续同一会话。A 的卡片只更新状态，不显示终端细节。
5. **需求变更隔离。** 执行期间 A 在卡片上补充“顺便加个退款导出”，补充只进入往来记录，不混入当前执行；扩充范围需要生成新方案版本并由 B 重新确认。
6. **结果回传与验收。** 执行完成后，同一张卡更新为“结果待 A 检查”，展示结论、测试证据、worktree 分支与最新 commit。A 选择“已检查，可以使用”或“需继续调整”；前者结束事项，后者在同一张卡上生成新方案版本。

## 演进方向

能力分三个交付阶段推进，当前交付范围与验收见 [mvp.md](mvp.md)。

- **交付阶段 1：事项卡与通知。** 从原工具创建问题卡和执行卡，在 inbox 页面展示，并通过本机系统通知和原工具钩子提醒接收方及其 Agent；接收方手动回复或关闭。
- **交付阶段 2：企业微信联动。** 通过企业微信自建应用或智能机器人推送按钮卡片、接收按钮回调并更新同一张卡，支持在卡片上唤起只读回答和验收结果。
- **交付阶段 3：唤起、确认与 worktree 执行交接。** 所有者唤起 Agent 生成方案、在确认单上批准，本地适配器派生 worktree 并拉起原生会话，结果回传事项卡。

后续可选增强：在宿主客户端证实可强制只读的前提下开启定向自动只读回答；对支持外部事件推送的宿主，将获批工作插入已打开的会话；按项目或仓库路由到不同客户端。

## Dev Note

本节非权威。交付阶段 2 与 3 的先后由用户按企业微信联动难度确定；执行交接已有本地脚本实测基础（见 mvp.md），如企业微信接入受阻，可考虑先做交付阶段 3。
